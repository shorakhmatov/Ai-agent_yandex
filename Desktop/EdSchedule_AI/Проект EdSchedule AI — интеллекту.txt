# Проект: EdSchedule AI — интеллектуальная платформа для образовательных учреждений

Ты — Senior Full-Stack Developer, Software Architect, UI/UX Designer, Database Engineer и специалист по информационной безопасности. Твоя задача — спроектировать и разработать полноценную, современную, безопасную и удобную образовательную платформу для школ, колледжей и университетов.

Работай как опытная команда разработки. Не ограничивайся демонстрационным интерфейсом, макетом или набором статических страниц. Создай реальное веб-приложение с работающим backend, frontend, базой данных, авторизацией, управлением расписанием и интеграцией ИИ.

Главный принцип проекта: **максимально упростить и ускорить создание, проверку, публикацию и изменение расписания преподавателей и учебных групп.**

## 1. Основная концепция

Платформа должна подходить для разных образовательных учреждений:

- Школы.
- Колледжи.
- Университеты.
- Учебные центры и другие образовательные организации.

Каждое учреждение должно иметь собственное изолированное рабочее пространство, пользователей, преподавателей, студентов, группы, кабинеты, предметы и расписания.

Платформа должна поддерживать несколько организаций одновременно. Данные одной организации не должны быть доступны другой организации.

Предусмотри архитектуру SaaS-платформы с возможностью дальнейшего масштабирования.

Название проекта: EdSchedule AI. Используй его как временное рабочее название, предусмотрев возможность изменения названия и логотипа.

Основной язык интерфейса — русский и узбекский. Архитектура должна позволять добавлять другие языки.

## 2. Технологический стек

Используй следующие технологии.

### Backend
- Python 3.12 или другая актуальная стабильная версия, совместимая с выбранными зависимостями.
- Django — основа серверной архитектуры.
- Django REST Framework — REST API.
- Django ORM — работа с базой данных.
- Celery и Redis — фоновые задачи, если они необходимы для генерации расписания и обработки ИИ-запросов.
- OpenAPI / Swagger — документация API.
- Gunicorn для production-развёртывания.

### Frontend
- React.
- TypeScript.
- Vite.
- Tailwind CSS.
- shadcn/ui или другой качественный компонентный UI-kit.
- Lucide Icons.
- TanStack Query для серверных данных.
- React Hook Form и Zod для форм и валидации.
- FullCalendar или собственный календарный интерфейс для отображения расписаний.

Если проект уже содержит подходящий frontend, сначала изучи его и не переписывай без необходимости.

### База данных
- Основной рекомендуемый вариант — MySQL 8.4 LTS.
- Если сервер поддерживает только MySQL 5.7 или другую старую версию, сначала проверь совместимость Django и всех необходимых функций.
- Не используй возможности базы данных, которые отсутствуют в целевой версии.
- Не выполняй автоматическое обновление базы данных и не изменяй существующую схему без разрешения.
- Используй миграции Django, индексы, внешние ключи и транзакции.
- Для тестирования можно использовать отдельную тестовую базу.

Если существующая база MySQL 5.x является обязательным ограничением, объясни ограничения и предложи совместимую реализацию.

### Дополнительные инструменты
- Git.
- Docker и Docker Compose для локальной разработки, если это уместно.
- Pytest и pytest-django.
- Playwright для сквозного тестирования интерфейса.
- Ruff для проверки Python-кода.
- ESLint и Prettier для frontend.
- Redis только для конкретных задач, где он действительно нужен.

Выбирай поддерживаемые и совместимые версии библиотек. Не устанавливай зависимости без необходимости.

## 3. Дизайн и пользовательский интерфейс

Создай современный, минималистичный и профессиональный интерфейс уровня качественного коммерческого SaaS-продукта.

Интерфейс должен быть простым даже для сотрудников, которые не обладают техническими знаниями.

### Визуальный стиль

- Светлая тема по умолчанию.
- Белый или светло-серый фон.
- Сдержанные синие, индиго или фиолетовые акценты.
- Хорошая типографика.
- Много свободного пространства.
- Понятная визуальная иерархия.
- Аккуратные карточки, таблицы и формы.
- Ненавязчивые анимации.
- Единая система отступов, цветов, размеров и состояний компонентов.
- Поддержка тёмной темы в будущем.
- Полная адаптивность для компьютеров, планшетов и мобильных устройств.

Не используй чрезмерное количество градиентов, теней, ярких цветов, декоративных элементов и ненужных анимаций.

Не делай интерфейс похожим на старую административную панель Django.

### Структура интерфейса

Основная рабочая область должна включать:

- Боковую панель навигации.
- Верхнюю панель с поиском, уведомлениями, профилем и выбором организации.
- Центральную рабочую область.
- Контекстные действия.
- Понятные состояния загрузки.
- Сообщения об ошибках.
- Подтверждения опасных операций.
- Пустые состояния с подсказками, объясняющими следующий шаг.

Создай переиспользуемые компоненты, чтобы все страницы выглядели единообразно.

## 4. Роли и права доступа

Реализуй ролевую систему доступа.

### Суперадминистратор платформы
- Управляет платформой и организациями.
- Просматривает системную статистику.
- Управляет глобальными настройками.
- Контролирует состояние фоновых задач и системные ошибки.
- Не получает произвольный доступ к персональным данным без предусмотренного разрешения и обоснованной необходимости.

### Администратор образовательного учреждения
- Настраивает организацию.
- Создаёт подразделения, факультеты и кафедры.
- Управляет пользователями и ролями.
- Добавляет преподавателей, студентов, предметы, группы и кабинеты.
- Настраивает учебные периоды.
- Создаёт и публикует расписания.

### Диспетчер или составитель расписания
- Импортирует учебные данные.
- Настраивает параметры генерации.
- Запускает автоматическое составление расписания.
- Исправляет конфликты.
- Перемещает занятия вручную.
- Сохраняет черновики и публикует расписание.

### Преподаватель
- Просматривает собственное расписание.
- Видит аудитории и учебные группы.
- Получает уведомления об изменениях.
- Может указать доступность и предпочтительное время занятий, если администратор разрешил такую возможность.

### Студент
- Просматривает расписание своей группы.
- Видит изменения и отмены занятий.
- Фильтрует занятия по дням и предметам.
- Может экспортировать расписание.

Реализуй разграничение доступа на сервере. Скрытие кнопок во frontend не считается защитой.

Проверяй разрешения при каждом защищённом API-запросе.

## 6. Основной модуль — автоматическое составление расписания

Это центральная функция всей платформы.

Создай полноценный механизм автоматической генерации расписаний с учётом ограничений и предпочтений.

### Исходные данные

Система должна учитывать:

- Преподавателей.
- Учебные группы.
- Предметы.
- Аудитории.
- Вместимость аудиторий.
- Доступное время преподавателей.
- Учебные дни.
- Временные интервалы.
- Количество часов по каждому предмету.
- Продолжительность занятий.
- Перерывы.
- Учебные смены.
- Совместные занятия нескольких групп.
- Лекционные и практические занятия.
- Специальные типы аудиторий.
- Предпочтения преподавателей.
- Праздничные и неучебные дни.
- Ограничения конкретного учреждения.

Сделай параметры настраиваемыми, поскольку расписания школы, колледжа и университета отличаются.

### Алгоритм генерации

Не используй случайное распределение занятий в качестве полноценного алгоритма.

Раздели ограничения на две категории.

**Жёсткие ограничения:**
- Преподаватель не может проводить два занятия одновременно.
- Одна учебная группа не может находиться на двух занятиях одновременно.
- Одна аудитория не может быть занята двумя занятиями одновременно.
- Вместимость и тип аудитории должны соответствовать требованиям занятия.
- Занятие должно попадать в разрешённое учебное время.
- Должно соблюдаться необходимое количество часов по предметам.
- Должны соблюдаться обязательные перерывы и другие установленные правила.

**Мягкие ограничения:**
- Предпочтительное время преподавателя.
- Минимизация окон в расписании.
- Равномерное распределение нагрузки.
- Минимизация ненужных перемещений между корпусами.
- Предпочтительные дни занятий.
- Удобное распределение сложных предметов.
- Снижение количества поздних занятий.
- Снижение количества свободных промежутков между занятиями.

Жёсткие ограничения нельзя нарушать ради улучшения мягких.

### Техническая реализация

Рассмотри Google OR-Tools CP-SAT как основной инструмент оптимизации расписания.

Создай отдельный сервис генерации, который:

1. Получает проверенные исходные данные.
2. Формирует задачу оптимизации.
3. Проверяет ограничения.
4. Выполняет поиск допустимого решения.
5. Оптимизирует мягкие ограничения.
6. Возвращает найденное расписание и его показатели.
7. Сообщает о невозможности решения, если условия несовместимы.
8. Показывает объяснение конфликтов и возможные способы их устранения.

Не утверждай, что расписание оптимально, если алгоритм не доказал оптимальность.

Предусмотри статусы:
- Ожидает выполнения.
- Выполняется.
- Найдено решение.
- Найдено допустимое решение.
- Решение не найдено.
- Не удалось завершить расчёт.
- Отменено.

Для длительных задач используй фоновые задания.

### Работа с расписанием

Пользователь должен иметь возможность:

- Генерировать расписание полностью.
- Генерировать расписание для выбранной группы.
- Генерировать расписание для определённого преподавателя.
- Пересоздавать расписание только для выбранной части, если это возможно без нарушения остальных ограничений.
- Редактировать занятия вручную.
- Перетаскивать занятия между временными слотами.
- Сразу видеть конфликты после изменения.
- Сравнивать варианты расписания.
- Сохранять несколько черновиков.
- Возвращаться к предыдущим версиям.
- Публиковать расписание.
- Отменять публикацию с соответствующими правами.
- Просматривать историю изменений.

Ручное редактирование не должно обходить проверку ограничений.

До публикации выполняй финальную серверную проверку конфликтов.

Если пользователь пытается выполнить несовместимое действие, объясняй причину простым языком.

## 7. ИИ-помощник

Создай встроенного ИИ-помощника, доступного из интерфейса платформы.

Он должен помогать пользователю работать с расписанием на естественном языке.

Примеры запросов:

- «Создай расписание для группы ИС-21».
- «Найди все конфликты на следующую неделю».
- «Покажи свободные аудитории в понедельник».
- «Найди преподавателей, у которых слишком много окон».
- «Предложи, как уменьшить количество окон».
- «Почему невозможно составить расписание для этой группы?».
- «Перенеси занятия преподавателя на доступное время» — только после проверки и подтверждения изменения.
- «Покажи расписание преподавателя Иванова».
- «Сравни два варианта расписания».
- «Подготовь отчёт о загрузке аудиторий».

### Принципы работы ИИ

ИИ не должен напрямую изменять базу данных.

Реализуй следующую архитектуру:

Пользователь → AI API → определение намерения → проверка разрешений → вызов разрешённого серверного инструмента → проверка результата → подтверждение при необходимости → выполнение → журналирование → ответ пользователю.

Используй инструментальный вызов функций (tool calling), если его поддерживает выбранная модель.

Создай отдельные безопасные инструменты, например:

- get_schedule.
- find_schedule_conflicts.
- get_available_rooms.
- get_teacher_workload.
- explain_generation_failure.
- propose_schedule_changes.
- generate_schedule.
- validate_schedule.
- publish_schedule.

Операции должны вызываться через серверные сервисы приложения, а не через произвольное выполнение кода или SQL.

ИИ должен:
- Объяснять результаты простым языком.
- Не придумывать отсутствующие данные.
- Отличать реальные данные от рекомендаций.
- Не обходить ограничения доступа.
- Не публиковать расписание без соответствующего разрешения и подтверждения.
- Запрашивать подтверждение перед существенными изменениями.
- Показывать пользователю перечень предполагаемых изменений.
- Проверять результаты после выполнения операций.

### Интеграция моделей

Создай абстрактный AI provider/service layer, позволяющий подключать разные совместимые модели через API.

Не привязывай всю бизнес-логику к одному поставщику.

API-ключи должны храниться только на сервере в переменных окружения или в защищённом хранилище секретов.

Предусмотри обработку тайм-аутов, ошибок, ограничений запросов и недоступности провайдера.

Не отправляй модели пароли, секреты, лишние персональные данные и полные базы пользователей.

Предусмотри возможность отключить ИИ без потери основных функций платформы.

Если ключ API отсутствует, покажи понятное сообщение и сохрани работоспособность обычного управления расписанием.

Создай полноценные CRUD-модули:

- Организации.
- Факультеты и кафедры.
- Преподаватели.
- Студенты.
- Учебные группы.
- Предметы.

- Учебные периоды.

- Расписание.

Перед импортом:

- Проверяй дубликаты.

## 9. Просмотр расписания

Создай несколько представлений:

- По неделям.
- По дням.
- По преподавателям.
- По учебным группам.
- По аудиториям.
- По предметам.
- По факультетам.
- По всему учреждению.

Добавь фильтры и быстрый поиск.

Каждое занятие должно содержать необходимую информацию: предмет, преподаватель, группа, аудитория, дата и время.

Используй разные, но спокойные цвета для категорий занятий, обеспечивая доступность интерфейса.

## 10. Безопасность

Поскольку платформа будет доступна через интернет, безопасность должна учитываться с самого начала разработки.

Следуй актуальным рекомендациям OWASP и рекомендациям Django по безопасности.

Обязательно реализуй:

- Защиту паролей средствами Django.
- Безопасную авторизацию и управление сессиями.
- Разграничение доступа по ролям и организациям.
- Защиту от IDOR и межорганизационного доступа.
- CSRF-защиту.
- Защиту от XSS.
- Параметризованные запросы через ORM.
- Серверную валидацию всех входящих данных.
- Ограничение частоты запросов на авторизацию и чувствительные API.
- Безопасную политику CORS.
- Безопасные настройки cookies.
- HTTPS в production.
- Настройки Secure, HttpOnly и SameSite для cookies согласно архитектуре.
- Защиту от массового назначения прав и повышения привилегий.

## 19. Критерии готовности MVP

MVP можно считать готовым, когда:

- Пользователь может безопасно войти в систему.
- Администратор может создать организацию и настроить её.
- Можно добавить преподавателей, группы, предметы и аудитории.
- Можно задать учебные ограничения.
- Генератор создаёт расписание, соблюдающее все жёсткие ограничения.
- При невозможности решения система объясняет причину.
- Пользователь может вручную менять расписание.
- Конфликтные изменения блокируются или требуют корректировки.
- Можно сохранить черновик и опубликовать расписание.
- Преподаватель может просмотреть собственное расписание.
- Студент может просмотреть расписание своей группы.
- ИИ-помощник умеет получать реальные данные и выполнять разрешённые операции через безопасные инструменты.
- ИИ не может самостоятельно обходить разрешения или публиковать изменения без предусмотренного подтверждения.
- Данные организаций изолированы друг от друга.
- Основные проверки безопасности покрыты тестами.
- Проект запускается по документации.
- Нет критических ошибок в основных пользовательских сценариях.

## 21. Отдельный кабинет заместителя директора и составителя расписания

Создай отдельный полноценный рабочий кабинет для заместителя директора или другого сотрудника, ответственного за составление учебного расписания.

Это одна из ключевых функций платформы. Кабинет должен быть максимально простым, понятным и удобным для ежедневной работы.

### Роль «Заместитель директора»

Добавь отдельную роль `Vice Principal` (заместитель директора), которую администратор образовательного учреждения может назначать конкретному сотруднику.

Предусмотри также возможность назначить сотрудника ответственным за расписание без предоставления ему всех полномочий администратора.

Пользователь с этой ролью должен иметь собственный интерфейс после входа в систему.

В кабинете должны быть следующие разделы:

1. **Главная панель**
   - Общее состояние учебного расписания.
   - Количество преподавателей, групп, предметов и аудиторий.
   - Количество запланированных занятий.
   - Количество обнаруженных конфликтов.
   - Статус текущей генерации расписания.
   - Последние изменения.
   - Быстрые действия для начала работы.

2. **Создание расписания**
   - Выбор учебного периода.
   - Выбор учебных дней и временных интервалов.
   - Выбор групп, преподавателей и предметов.
   - Выбор доступных аудиторий.
   - Настройка продолжительности занятий и перерывов.
   - Настройка нагрузки преподавателей.
   - Указание доступности преподавателей.
   - Настройка дополнительных ограничений учреждения.
   - Запуск автоматической генерации расписания.

3. **Проверка расписания**
   - Просмотр всех найденных конфликтов.
   - Понятное объяснение каждой ошибки.
   - Рекомендации по устранению конфликтов.
   - Просмотр свободных временных интервалов.
   - Просмотр свободных аудиторий.
   - Проверка распределения нагрузки преподавателей.
   - Проверка количества часов по каждому предмету.

4. **Редактирование расписания**
   - Визуальный календарь с возможностью перетаскивать занятия.
   - Ручное изменение времени, преподавателя, группы и аудитории.
   - Автоматическая проверка конфликтов после каждого изменения.
   - Сохранение изменений в черновике.
   - Возможность отменить последнее действие.
   - Возможность сравнивать разные версии расписания.
   - Предупреждение о потенциальной потере несохранённых изменений.

5. **Управление версиями**
   - Создание нескольких вариантов расписания.
   - Сохранение черновиков.
   - Просмотр истории изменений.
   - Сравнение версий.
   - Восстановление предыдущей версии с соблюдением прав доступа.
   - Публикация утверждённого расписания.

6. **Экспорт и скачивание**
   - Скачать расписание всего учреждения.
   - Скачать расписание отдельной группы.
   - Скачать расписание отдельного преподавателя.
   - Скачать расписание конкретной аудитории.
   - Выбрать учебный период или диапазон дат.
   - Выбрать нужный формат файла.
   - Скачать расписание на русском или узбекском языке.

### Разграничение полномочий

Заместитель директора должен иметь право управлять расписанием в пределах назначенной ему организации и предоставленных разрешений.

При этом он не должен автоматически получать доступ к:
- Глобальным настройкам платформы.
- Управлению другими организациями.
- Секретам и API-ключам.
- Настройкам безопасности, доступным только суперадминистратору.
- Другим административным функциям, не связанным с его работой.

Предусмотри настраиваемые разрешения: например, один сотрудник может создавать и редактировать расписание, а другой — только проверять его и готовить к публикации.

Если по правилам учреждения публикацию должен подтверждать директор, реализуй отдельный процесс утверждения: заместитель директора создаёт и проверяет расписание, отправляет его на утверждение, а уполномоченный руководитель публикует его.

Если учреждение не требует такого согласования, администратор может разрешить заместителю директора самостоятельно публиковать расписание.

Все действия с расписанием должны фиксироваться в журнале аудита.

### Правила мультиязычности

1. По умолчанию используй русский язык, если пользователь не выбрал другой язык.
2. Узбекский интерфейс должен быть полноценным, а не частично переведённым.
3. Переводи все элементы интерфейса: меню, кнопки, формы, таблицы, подсказки, уведомления, сообщения об ошибках, страницы входа, кабинет заместителя директора и ИИ-помощника.
4. Переводи системные сообщения, отчёты и названия доступных действий.
5. Учитывай язык при формировании PDF, XLSX и других экспортируемых файлов.
6. Сохраняй выбранный язык пользователя между посещениями.
7. Предусмотри отдельные языковые настройки для каждого пользователя.
8. Не дублируй бизнес-логику для каждого языка.
9. Используй централизованную систему локализации Django и frontend.
10. Не размещай пользовательские строки непосредственно в компонентах, если они должны переводиться.

### Узбекская локализация

Поддерживай узбекский язык в латинской графике как основной вариант: `uz`.

Предусмотри корректное отображение символов Oʻ, Gʻ, oʻ, gʻ и других символов узбекского языка.

Архитектура должна позволять в дальнейшем добавить узбекскую кириллицу, если это потребуется.

Все шрифты, экспортируемые документы и PDF должны корректно отображать русские и узбекские символы.

### Перевод учебных данных

Разделяй системный интерфейс и пользовательские данные.

Например, названия предметов, факультетов и учебных групп могут вводиться самим учреждением. Не переводи автоматически официальные названия без необходимости.

Для системных обозначений используй локализованные подписи. Если предусмотрены двуязычные названия предметов или подразделений, храни их отдельно и позволяй выбрать язык отображения.

Даты, дни недели, время и календарные обозначения должны форматироваться с учётом выбранной локали.

### ИИ-помощник на двух языках

ИИ-помощник должен понимать и обрабатывать запросы на русском и узбекском языках.

Примеры запросов на русском:
- «Создай расписание для группы ИС-21».
- «Найди свободные аудитории на понедельник».
- «Покажи конфликты в расписании преподавателей».

Примеры запросов на узбекском:
- «ИС-21 гуруҳи учун дарс жадвалини туз».
- «Душанба куни бўш аудиторияларни кўрсат».
- «Ўқитувчилар жадвалидаги зиддиятларни топ».

Это примеры пользовательских запросов, а не жёстко заданный список поддерживаемых команд.

ИИ должен определять язык запроса, учитывать язык интерфейса и отвечать на подходящем языке. Он должен использовать реальные данные организации и те же проверки доступа, что и обычные API-запросы.

Если модель плохо обрабатывает конкретную языковую формулировку, система должна корректно попросить уточнить запрос, а не выполнять потенциально опасное действие.

## 23. Скачивание и экспорт расписания в нескольких форматах

Создай полноценный модуль экспорта расписаний, доступный в кабинете заместителя директора, административном интерфейсе и других разделах в соответствии с правами пользователя.

Добавь заметную кнопку «Скачать расписание» с меню выбора формата и параметров экспорта.

### Поддерживаемые форматы

**1. PDF**
- Аккуратно оформленный документ для печати.
- Название образовательного учреждения.
- Название группы или имя преподавателя, если применимо.
- Учебный период.
- Таблица расписания.
- Дни недели и время занятий.
- Названия предметов, преподавателей и аудиторий.
- Дата формирования документа.
- Поддержка русского и узбекского языков.
- Корректные шрифты для кириллицы и узбекских символов.
- Формат страницы A4 с подходящей ориентацией.

**2. Excel — XLSX**
- Удобная таблица с заголовками.
- Отдельные листы для выбранных групп или преподавателей, если это уместно.
- Фильтры и форматирование.
- Подходящая ширина столбцов.
- Возможность дальнейшего редактирования документа.
- Корректное отображение всех поддерживаемых языков.

**3. CSV**
- Экспорт табличных данных для обработки в других системах.
- Явное указание кодировки UTF-8.
- Корректная обработка разделителей и специальных символов.
- Возможность выбора разделителя, если это необходимо для совместимости с табличными редакторами.

**4. ICS — календарный формат**
- Возможность импортировать занятия в совместимые календарные приложения.
- Корректные даты и время.
- Поддержка часового пояса организации.
- Название занятия, время начала и окончания, место проведения.
- Стабильные идентификаторы событий.
- Корректная обработка обновлений и отмен занятий при повторном импорте, где это поддерживается.

**5. HTML для печати**
- Отдельная чистая страница расписания без элементов управления платформы.
- Возможность открыть системное окно печати браузера и сохранить документ в PDF.
- Адаптивная таблица и удобное оформление.

### Параметры экспорта

Перед скачиванием пользователь должен иметь возможность выбрать:

- Всё учреждение или отдельную группу.
- Одного преподавателя.
- Одну аудиторию.
- Учебную неделю, месяц или другой период.
- Опубликованную версию или доступный ему черновик.
- Язык документа: русский или узбекский.
- Формат файла.

Показывай только те параметры, которые подходят выбранному формату.

### Требования к безопасности экспорта

- Проверяй разрешения пользователя перед формированием файла.
- Не позволяй скачивать данные другой организации.
- Не включай в файл скрытые персональные данные.
- Не экспортируй черновики пользователям, которым они недоступны.
- Не помещай секреты и внутренние идентификаторы безопасности в документ.
- Защищай экспорт от CSV Formula Injection при открытии файлов в табличных редакторах.
- Ограничивай чрезмерно большие запросы на экспорт.
- Для больших файлов используй фоновые задачи.
- Если формирование документа занимает время, показывай статус и предоставляй скачивание после завершения.
- Временно храни сформированные файлы и обеспечивай ограниченный срок их доступности.
- Проверяй права доступа повторно при скачивании готового файла.

### Критерии готовности экспорта

Экспорт считается реализованным, если пользователь может выбрать необходимые параметры, получить файл выбранного формата, открыть его в соответствующем приложении и увидеть корректное расписание на русском или узбекском языке.

Не создавай кнопки скачивания, которые ведут на несуществующие маршруты или возвращают фиктивные файлы.

## 24. Дополнительные критерии готовности MVP

Помимо основных требований проекта, обязательно проверь:

- У заместителя директора есть отдельный рабочий кабинет.
- Заместитель директора может создавать, проверять и редактировать расписание в пределах своих полномочий.
- При необходимости реализован процесс утверждения расписания директором.
- Переключение между русским и узбекским языками работает на всех основных страницах.
- Выбранный язык сохраняется в настройках пользователя.
- ИИ-помощник принимает запросы на обоих языках.
- Расписание можно скачать в PDF, XLSX, CSV, ICS и HTML для печати.
- Экспорт учитывает выбранную группу, преподавателя, период и язык.
- Все форматы содержат корректные даты, время и названия занятий.
- Русские и узбекские символы правильно отображаются в экспортируемых документах.
- Пользователь не может скачать расписание или данные, к которым у него нет доступа.
- Все основные функции покрыты автоматическими тестами.

**Общий принцип:** создай не просто интерфейс с переключателем языка и кнопкой скачивания, а действительно работающую мультиязычную систему с полноценным кабинетом составителя расписания и надёжным экспортом данных.

## 25. Максимально простое и быстрое создание расписания — главный приоритет UX

Это одно из самых важных требований всего проекта.

Создай процесс составления расписания, которым заместитель директора или диспетчер сможет пользоваться без специальных технических знаний. Пользователь не должен тратить много времени на заполнение форм, переходить между десятками страниц или самостоятельно искать конфликты.

**Главный принцип: пользователь предоставляет исходные данные и основные требования, а система делает всю сложную работу автоматически.**

### 1. Создание расписания в несколько простых шагов

Реализуй единый мастер создания расписания (Schedule Wizard) с понятным пошаговым интерфейсом.

Не показывай все настройки сразу. Раздели процесс на несколько коротких этапов.

**Шаг 1. Выбор учебного периода**

Пользователь выбирает:
- Учебный год или семестр.
- Дату начала и окончания, если необходимо.
- Дни, в которые проводятся занятия.
- Время начала и окончания учебного дня.

По возможности предлагай ранее использованные настройки и готовые шаблоны.

**Шаг 2. Добавление учебных данных**

Предложи три простых способа:
- Выбрать уже добавленные данные.
- Импортировать преподавателей, группы, предметы и аудитории из Excel или CSV.
- Добавить необходимые данные вручную через короткие формы.

Если необходимые данные уже есть в системе, не требуй вводить их повторно.

При импорте покажи предварительный просмотр и автоматически определи столбцы, если это возможно. Ошибки объясняй простым языком.

**Шаг 3. Настройка правил**

Показывай только основные настройки:
- Продолжительность занятий.
- Количество занятий или часов по предметам.
- Рабочее время преподавателей.
- Ограничения по аудиториям.
- Перерывы.
- Другие обязательные требования учреждения.

Используй разумные значения по умолчанию и позволяй менять их при необходимости.

Дополнительные настройки помести в раскрывающийся раздел «Дополнительные параметры». Не перегружай ими обычного пользователя.

**Шаг 4. Автоматическая проверка**

До генерации система сама проверяет, достаточно ли данных для создания расписания.

Например:
- У всех ли предметов назначены преподаватели.
- Есть ли доступные аудитории.
- Указано ли необходимое количество часов.
- Нет ли несовместимых ограничений.
- Достаточно ли временных интервалов для размещения занятий.

Показывай понятный результат проверки.

Пример:
- «Все данные готовы к созданию расписания».
- «У 2 предметов не назначены преподаватели».
- «Для группы ИС-21 недостаточно свободных временных интервалов».

Добавляй кнопку перехода непосредственно к исправлению каждой найденной проблемы.

**Шаг 5. Создание расписания**

Сделай одну заметную основную кнопку:

«Создать расписание автоматически».

После нажатия система должна:
1. Проверить права пользователя и актуальность данных.
2. Запустить генерацию расписания.
3. Показывать статус процесса и понятное описание текущего этапа.
4. Не блокировать интерфейс во время длительных вычислений.
5. После завершения показать результат.
6. Если решение не найдено, объяснить причины и предложить варианты исправления.

Не показывай пользователю технические логи, сложные математические термины и внутренние детали алгоритма.

**Шаг 6. Проверка и публикация**

После генерации открой готовое расписание в визуальном календаре.

Покажи:
- Найдено ли допустимое решение.
- Есть ли конфликты.
- Насколько равномерно распределена нагрузка.
- Какие проблемы требуют внимания.
- Какие действия доступны дальше.

Добавь три понятных действия:
- «Сохранить черновик».
- «Исправить расписание».
- «Опубликовать расписание» — только при наличии необходимых разрешений и после всех обязательных проверок.

Не заставляй пользователя проходить повторно все предыдущие шаги, если ему нужно только исправить одну ошибку.

### 2. Режим «Создать расписание быстро»

Помимо пошагового мастера, добавь максимально быстрый сценарий для пользователей, у которых учебные данные уже подготовлены.

Пользователь выбирает учебный период, при необходимости указывает группы или подразделения и нажимает одну кнопку.

Система автоматически:
- Загружает необходимые данные.
- Использует сохранённые настройки.
- Проверяет ограничения.
- Находит конфликты.
- Запускает генерацию.
- Открывает результат для проверки.

Если каких-то обязательных данных не хватает, не завершай процесс непонятной ошибкой. Покажи только необходимые вопросы и предложи заполнить недостающие данные.

### 3. ИИ-помощник как простой способ создания расписания

Добавь возможность создавать расписание с помощью естественного языка.

Например, пользователь пишет:

«Создай расписание на следующий семестр для всех групп. Занятия проводятся с понедельника по субботу с 8:30 до 17:00. Учитывай доступность преподавателей и старайся минимизировать окна».

ИИ должен:
1. Понять запрос.
2. Проверить доступные данные и права пользователя.
3. Определить, каких обязательных сведений не хватает.
4. Задать только необходимые уточняющие вопросы.
5. Сформировать понятное резюме параметров.
6. Запустить генерацию через основной алгоритм расписания.
7. Показать результат и объяснить обнаруженные проблемы.

Если пользователь не указал необязательные параметры, используй сохранённые настройки учреждения.

ИИ не должен самостоятельно придумывать преподавателей, предметы, аудитории или обязательные ограничения.

Перед публикацией расписания обязательно соблюдай установленный процесс подтверждения.

### 4. Шаблоны и повторное использование

Добавь возможность сохранять настройки создания расписания в виде шаблонов.

Например:
- «Школа — первая смена».
- «Школа — вторая смена».
- «Колледж — стандартное расписание».
- «Университет — лекции и практические занятия».

Это примеры названий, а не жёстко заданные правила.

Пользователь должен иметь возможность создать собственный шаблон, изменить его и использовать повторно.

Предусмотри копирование расписания предыдущего семестра или учебного периода с последующей проверкой актуальности преподавателей, групп, аудиторий и ограничений.

Не публикуй скопированное расписание автоматически.

### 5. Максимально удобное исправление ошибок

Если расписание невозможно создать, система не должна просто показывать «Ошибка генерации».

Вместо этого объясняй ситуацию понятным языком.

Например:

«Не удалось разместить все занятия группы ИС-21. В среду у преподавателя уже есть занятие, а в четверг все подходящие аудитории заняты».

Предлагай варианты:
- Выбрать другое время.
- Найти альтернативную аудиторию.
- Проверить доступность преподавателя.
- Изменить необязательные предпочтения.
- Повторить генерацию с разрешёнными изменениями.

Не меняй жёсткие ограничения автоматически. Любое изменение исходных требований должно быть явно показано пользователю и подтверждено, если оно влияет на правила учреждения.

### 6. Удобный интерфейс и минимум действий

При проектировании обязательно соблюдай следующие правила:

- Одна основная задача — один понятный экран.
- Одна главная кнопка для следующего действия.
- Минимум обязательных полей.
- Автоматическое заполнение известных значений.
- Сохранение промежуточных результатов.
- Понятный индикатор прогресса.
- Краткие пояснения рядом со сложными настройками.
- Отсутствие ненужных всплывающих окон.
- Возможность вернуться на предыдущий шаг без потери введённых данных.
- Адаптивная работа на компьютерах, планшетах и смартфонах.
- Полная локализация всех шагов на русский и узбекский языки.

Не делай сложную многостраничную административную форму основным способом создания расписания.

### 7. Проверка удобства использования

Проверь основной пользовательский сценарий:

1. Заместитель директора входит в систему.
2. Выбирает учебный период.
3. Загружает или выбирает учебные данные.
4. Нажимает кнопку автоматического создания расписания.
5. Получает готовый вариант.
6. Исправляет при необходимости отдельные занятия.
7. Сохраняет и публикует расписание.
8. Скачивает результат в нужном формате.

Стремись к тому, чтобы при заранее подготовленных данных пользователь мог начать генерацию всего за несколько действий.

Измеряй количество обязательных действий, время прохождения сценария и количество ошибок пользователя. Устраняй ненужные шаги, если они не требуются для безопасности или корректности.

**Итоговое требование:** составление расписания должно ощущаться как простая автоматизированная задача, а не как сложная работа с большой административной системой. Пользователь задаёт основные условия, нажимает кнопку и получает проверенный результат, который при необходимости может легко исправить.
